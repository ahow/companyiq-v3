# `sample-filing.pdf` — pdf-parse test fixture

A small, well-formed PDF used by the pdf-parse subprocess tests
(`pdf-parse-subprocess-equivalence.test.ts`, `stalled-extraction-boundary.test.ts`)
as a document the real `pdf-parse` library can extract text from.

## Why a committed binary and not `marker-pdf.ts`

`pdf-parse@1.1.4` bundles an old pdf.js (v1.10.100) whose cross-reference reader
rejects the minimal hand-built xref tables produced by `__fixtures__/marker-pdf.ts`
(it throws `bad XRef entry` and then its first-call recovery path is itself buggy).
`marker-pdf.ts` is fine for the real-browser → `pdftotext` (poppler) path, which is
lenient, but it cannot drive the `pdf-parse` path. This fixture is generated by a
real engine (weasyprint) that emits an xref pdf.js accepts on the first call.

## Deterministic regeneration

```bash
cat > /tmp/fx.html <<'HTML'
<!DOCTYPE html><html><head><meta charset="utf-8">
<style>@page{size:letter;margin:1in}body{font-family:sans-serif;font-size:12pt}</style></head>
<body>
<p>CIQMARKER-ALPHA equivalence fixture line one.</p>
<p>Row A 10 20 30 and Row B 40 50 60 table-ish content for the horizon normaliser.</p>
<p>Padding sentence to comfortably exceed the pdf-parse minimum character threshold so extraction stays on the primary path.</p>
</body></html>
HTML
SOURCE_DATE_EPOCH=1700000000 weasyprint /tmp/fx.html server/lib/__fixtures__/sample-filing.pdf
```

`SOURCE_DATE_EPOCH` makes the output byte-identical run to run
(md5 `16cafad79d75d6c7c7980a12bf99e439`). Extracted text is 249 chars and is
byte-identical via in-process pdf-parse and via the subprocess worker.
